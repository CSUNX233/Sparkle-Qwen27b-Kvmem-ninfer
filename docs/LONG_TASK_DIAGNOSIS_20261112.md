# 长任务写入、压缩与掉线诊断（2026-11-12）

## 写入误拒绝

一次制作交互内容的任务包含“查看介绍”功能。`edit-guard` 把功能描述中的“查看”识别成用户的纯读取意图，随后拦截 `write` 并要求修改一个空目标路径。它是实际观察到的失败，和模型生成内容不足、显存不足无关。

修复：读取或切换类型的推断只有在用户明确要求只读时才拦截写操作；其他文件目标与精确编辑检查保持原有路径。完整 13 项测试通过，包含真实 dsh 工具管线创建文件、明确只读阻止写入、单文件精确编辑保护。已更新本机插件和此源码树；**已有发布附件尚未更新**。此前版本的源码中也有相同判断，无法仅凭这次失败断定 1.1 引入该缺陷。

## 压缩后多图续接

历史记录中 `compaction/summary`、`compaction/end` 确实已写入，随后两次模型请求均以 `scatter: expected src [D,V], indices [V], dst [D,T]` 失败。该错误的具体调用点和根因尚未定位，不能称为已修复。

目前单图、7 图合成长历史均可运行；对失败会话的本机隔离冷重放，99 条消息、7 图、61 个工具、约 71K 输入顺利完成预填充。重放未执行工具，不写回原会话；受输出上限及消息重建差异影响，它不是字节级原请求重放。此前 1.0 和 1.1 的 scatter 实现及视觉前向文件相同，但这不能排除其他改动或缓存状态触发该问题。

同一隔离进程先重放压缩前 200 条消息、12 图和 186088 输入 token，接着重放压缩后 99 条消息、7 图和 71278 输入 token；两次均完成预填充，没有 `scatter` 异常。第二次缓存命中是 **0%**，所以不能用它证明实际缓存复用路径无缺陷。两次诊断输出上限均为128 token，输出达到长度上限不代表原始任务成功。两次生成的工具调用均未执行，原会话未写回。

真实 dsh 自动压缩的合成长任务：25 个工具结果、压缩前 TokenMeter 估算 **199998 tokens**，压力触发后记录 `compaction/start`、`compaction/summary` 和 `compaction/end`，表面降至 **32558 tokens**。摘要引擎实际输入 97135 tokens、正常结束，摘要包含两个分布在不同工具结果中的预埋准确值。估算值与模型 tokenizer 的输入计数不是同一指标。

压缩后的续接请求已开始预填充，但本机提交空间低于 512 MiB 时，为保护其他程序主动停止了隔离引擎；后续 guard 的断连、重试和测试请求预算耗尽均由此次主动停止造成。**摘要和两项事实保留通过，最终续接答案未验证**，不能把中断算作引擎自身崩溃或完整任务通过。

## cache_guard 掉线报告

`GUARD_HEAL=1` 控制历史消息字节修复，不启动健康检查，也不会自行重启代理。`listening` 日志显示服务启动过，不能单凭多条启动记录区分手动重启、脚本重启或异常退出。

一份外部故障报告称发生了 Event ID 2004，且系统提交额度逼近上限。若原始事件和性能计数确认，这种提交压力足以导致分配失败，是值得优先排查的因素；但报告没有提供代理退出码、进程终止事件或与每次断线一一对应的证据，不能认定系统已杀掉代理。Event 2004 本身不证明代理是受害进程，也不能将 Windows 机制直接称为固定的 Linux 式 OOM killer。

建议检查同一时刻的提交量/提交上限、Event 2004 原文、应用程序错误及 guard stderr/PID；优先考虑由 Windows 管理页面文件并确保磁盘有空间。降低 Host KV 是另一种释放内存的选择，可能增加长上下文重新预填充，须由使用者权衡。不要盲目运行来源不明的注册表写入或重启命令。

现有代理 HTTP 测试覆盖正常响应、客户端取消、上游错误、部分流中断、压缩 checkpoint，以及 6 秒空闲的活动 SSE；8 项通过。这不证明对方机器长时间高负载稳定，也不证明内存耗尽时代理能继续运行。
